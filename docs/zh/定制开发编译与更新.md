## 1. 目录与版本

工作区在 `D:\electron`。Electron 源码、Chromium 树、编译机和镜像是四套目录，不要混用。

| 位置 | 路径 | 作用 |
|------|------|------|
| 本机 gclient 根 | `D:\electron\main` | `.gclient`、`src\`。Windows 编译在这里进行 |
| Electron | `D:\electron\main\src\electron` | fork 源码，分支 `45-x-y` |
| Chromium | `D:\electron\main\src` | 由 `e sync` 按 `DEPS` 检出，再打补丁 |
| Windows 产物 | `D:\electron\main\src\out\Release\dist.zip` | 含 `electron.exe`。镜像默认读这个文件 |
| 编译机 | `/home/electron-build` | Linux 编译。容器内 `/src` 对应宿主机 `workspace/` |
| 镜像 | `D:\electron\mirror` | 把 `dist.zip` 发布成 npm 包和二进制 |

两套版本号：

| 名字 | 例子 | 谁在用 |
|------|------|--------|
| 分支 | `45-x-y` | 跟上游 Electron 大版本。源码推这个分支 |
| 发布号 | `45.0.0-cloudbypass.5`（当前 Windows 发行版本）；Linux 仍为已有 `.2` | `mirror/config.json` 与对应平台产物。业务项目固定所用平台已发布的完整版本号 |

`process.versions.electron` 来自 Electron 仓库里最近的 git tag（`git describe --tags --abbrev=0`），可以和发布号不一致。安装、升级、对账都以发布号为准。

本机 remote：

| remote | fetch | push |
|--------|-------|------|
| `fork` | `ChengHoward/electron` | 同一地址。日常推送用这个 |
| `origin` | 上游 `electron/electron` | 推送 URL 也指向 fork，但 fetch 是上游。升大版本时用它拉 `NN-x-y` |

编译机容器里的 `origin` 被 `xbuild-init` 固定成 `https://github.com/ChengHoward/electron`。容器里的 `git fetch origin` 拉的是 fork，不是上游。

`.gclient` 里 `src/electron` 的 `managed` 为 `False`：`e sync` 不会帮你切 Electron 分支，分支要自己 checkout。Mac 专用依赖在 Windows / Linux 上关掉：

```python
"custom_deps" : {
  "src/third_party/jetstream/v3.0": None,
  "src/third_party/squirrel.mac": None,
  "src/third_party/squirrel.mac/vendor/ReactiveObjC": None,
  "src/third_party/squirrel.mac/vendor/Mantle": None,
  "src/third_party/squirrel.mac/vendor/Sparkle": None,
},
```

改过 `custom_deps` 后，同步前删掉 gclient 根下的 `.gclient_entries`，否则 gclient 会沿用旧依赖表。

## 2. 定制开发

在 `D:\electron\main\src\electron` 的 `45-x-y` 上改。推上去之后，编译机再 fetch 同一分支。

### 2.1 只改 Electron

直接改并提交这些树：

| 路径 | 内容 |
|------|------|
| `shell/` | C++ API、浏览器侧行为 |
| `lib/` | JS 封装 |
| `typings/`、`electron.d.ts` | 类型 |
| `docs/api/` | 上游风格 API 说明 |
| `filenames.gni`、`BUILD.gn` | 新源文件要登记 |
| `spec/`、`test/` | 规格与定制测试 |

Chromium 树不要靠未提交的工作区改动当唯一副本。

### 2.2 改 Chromium：必须进补丁

Chromium 改动放在 `patches/chromium/*.patch`，并在 `patches/chromium/.patches` **末尾**追加文件名。`e sync` 会按这个清单 `git am`。

当前 fork 在上游 Electron 补丁之后额外挂了：

| 补丁 | 作用 |
|------|------|
| `fix_allow_ua_override_when_main_frame_is_remote.patch` | 跨域 OOPIF 仍启用 UA 覆盖 |
| `feat_navigator_platform_override_in_renderer_preferences.patch` | `navigator.platform` |
| `feat_hide_chrome_in_renderer_preferences.patch` | 隐藏网页 `window.chrome` |
| `feat_web_input_element_set_files_from_paths.patch` | `setFileInputFiles` |
| `feat_carry_proxy_username_and_password_on_proxyserver.patch` | 代理用户名和密码 |

其它依赖（boringssl、v8、node 等）用 `patches/<repo>/`，登记关系在 `patches/config.json`。

新增或修改补丁的做法：

1. 在已经打过补丁的 Chromium 树上改代码，并在 `src` 仓库里提交。
2. 在 gclient 根执行导出（会按 Chromium 提交重写 `patches/chromium` 里的 `.patch` 和 `.patches`）：

```powershell
cd D:\electron\main
python src\electron\script\export_all_patches.py src\electron\patches\config.json
```

导出前确认 Chromium 历史上要保留的提交都在。脚本会删掉目录里旧的 `.patch` 再按提交重写。

小改动也可以手改已有 `.patch`，或新增一个 `.patch` 后把文件名追加到 `.patches` 最后一行。下次同步会应用它。

补丁应用入口是 `script/apply_all_patches.py`。手动重打时必须在 **gclient 根**执行，这样 `config.json` 里的 `src/...` 才解析得对：

```bash
cd /src
python3 src/electron/script/apply_all_patches.py src/electron/patches/config.json
```

### 2.3 提交并推送

```powershell
cd D:\electron\main\src\electron
git status -sb
git push fork HEAD:45-x-y
```

功能说明、变更简述、变更详细放在 `D:\electron\main\docs`，并同步一份到 `src/electron/docs/zh`（fork 仓库里的中文文档）。两处一起改。

### 2.4 同步时会丢掉的东西

- Chromium 工作区里没进补丁、也没提交的修改。`e sync`、`git reset --hard`、`git clean` 都会清掉。
- 在 Chromium 仓库里执行 `git clean` 时，`electron/` 和 `out/` 对它来说像未跟踪目录。清理必须排除它们：`git clean -ffd -e electron -e out`。
- 上一个大版本的 `src/out`。换 Chromium 大版本后应删掉再编，避免旧构建目录混进新树。

## 3. 编译

Windows 与 Linux 各编各的。不能从 Windows 交叉编译 Linux，也不能从 Linux 交叉编译 Windows。同一发布号可以先后发布两个平台，校验和文件会合并。

编之前 Electron 目录必须已经是要发布的提交：

```powershell
cd D:\electron\main\src\electron
git fetch fork
git checkout 45-x-y
git pull fork 45-x-y
```

### 3.1 Windows（本机）

日常用 `D:\electron\xbuild\ebuild`。它会检查并写上 Node、Python、Git、depot_tools、`e` 和代理，再调用 `e sync` / `e build`。远程编译还没接。

```powershell
cd D:\electron\xbuild\ebuild
.\ebuild.cmd setup
.\ebuild.cmd doctor
.\ebuild.cmd build --branch 45-x-y
```

缺程序时用 `.\ebuild.cmd setup --install`。说明见 `xbuild\ebuild\README.md`。

底下仍是它调用的命令。gclient 根是 `D:\electron\main`：

```powershell
cd D:\electron\main
e sync --three-way
e build electron:electron_dist_zip
```

已有 `out\Release`、且这次只改 Electron / 补丁已经打上时，可以在 `src` 目录增量编：

```powershell
cd D:\electron\main\src
ninja -C out\Release electron:electron_dist_zip
```

产物：

- `D:\electron\main\src\out\Release\electron.exe`
- `D:\electron\main\src\out\Release\dist.zip`（压缩包内应有 `electron.exe`）

`e sync` 在补丁冲突时停下。处理见 [§5.2](#52-补丁冲突)。

### 3.2 Linux（编译机）

环境细节、磁盘和容器排障见 `D:\electron\xbuild\README.md`。这里是日常命令。宿主机登录信息不要写进仓库。

```bash
ssh -p <SSH_PORT> <USER>@<HOST>
cd /home/electron-build/xbuild
docker compose up -d
docker compose exec xbuild bash
```

容器内：

```bash
cd /src/src/electron
git fetch origin 45-x-y
git checkout -B 45-x-y origin/45-x-y
git log -1 --oneline

cd /src
nice -n 15 e sync --three-way
nice -n 15 e build -j80 electron:electron_dist_zip
```

机器大约 88 逻辑核，默认 `-j80`。宿主机上还有别的服务时，把并行降到 `-j32`，并保持 `nice -n 15`。只结束容器里的 `e build` / `ninja`，不要停宿主机上其它容器。

`e build` 已经包含链接时，打包可以单独重跑：

```bash
cd /src/src
nice -n 15 ninja -C out/Release electron:electron_dist_zip
```

产物在容器 `/src/src/out/Release/`，宿主机对应：

```text
/home/electron-build/workspace/src/out/Release/electron
/home/electron-build/workspace/src/out/Release/dist.zip
```

长时间任务写到 gclient 根下的日志（宿主机同样能看到）：`sync*.log`、`build.log`、`dist.log`。结束行是 `EXIT:0` 或脚本里的 `SYNC_EXIT` / `BUILD_EXIT`。

确认 zip 里是 Linux 二进制 `electron`，而不是 `electron.exe`，再拷回本机发布。

### 3.3 换大版本时先清构建目录

```bash
# 编译机
rm -rf /home/electron-build/workspace/src/out
```

```powershell
# 本机
Remove-Item -Recurse -Force D:\electron\main\src\out
```

然后重新 `e sync --three-way` 和 `e build`。同一大版本里的增量修改不必删 `out`。

## 4. 发布与业务项目更新

发布号写在 `D:\electron\mirror\config.json` 的 `version`。每次对外给出的二进制都用新的发布号（例如 `.2` 提到 `.3`）。`@electron/get` 按版本缓存 zip，同一版本覆盖文件后，已经装过的环境不会自动重下。

### 4.1 发布 Windows

默认 `platform` / `arch` 是 `win32` / `x64`，zip 路径是 `../main/src/out/Release/dist.zip`。

```powershell
cd D:\electron\mirror
# 编辑 config.json 的 version，例如 45.0.0-cloudbypass.3
npm run publish
```

服务已在跑时不用重启，它读的是 `mirror/data/`。

### 4.2 再发布 Linux（同一版本号）

本节是具备对应 Linux 构建时的通用流程，保留历史命令与 `.2` 双平台示例。本次 `.5` 只发行 Windows x64，不执行本节；现有 Linux x64 仍为 `45.0.0-cloudbypass.2`。

把编译机的 `dist.zip` 拷回本机后：

```powershell
cd D:\electron\mirror
$env:ELECTRON_MIRROR_VERSION = "45.0.0-cloudbypass.3"
$env:ELECTRON_MIRROR_PLATFORM = "linux"
$env:ELECTRON_MIRROR_ARCH = "x64"
$env:ELECTRON_MIRROR_DIST_ZIP = "D:\path\to\linux-dist.zip"
npm run publish
```

`SHASUMS256.txt` 按文件名合并，后一次发布会保留同版本里已有平台的校验和。`45.0.0-cloudbypass.2` 因此同时有：

- `electron-v45.0.0-cloudbypass.2-win32-x64.zip`
- `electron-v45.0.0-cloudbypass.2-linux-x64.zip`

发布完检查：

```text
https://mirror.cloudbypass.com/electron/v<version>/SHASUMS256.txt
https://mirror.cloudbypass.com/electron/npm/electron
```

### 4.3 业务项目改依赖

项目根 `.npmrc` 保持：

```ini
registry=https://registry.npmjs.org/
electron_mirror=https://mirror.cloudbypass.com/electron/
electron_custom_dir=v{{ version }}
electron_use_remote_checksums=1
```

然后只把 Electron 指到新发布号：

```bash
yarn add electron@45.0.0-cloudbypass.3 --registry https://mirror.cloudbypass.com/electron/npm/
```

全局 `registry` 仍用官方 npm。二进制由 `postinstall` 按 `electron_mirror` 下载，校验和必须走远端 `SHASUMS256.txt`。

## 5. 升到新的 Electron 大版本

例如从 `44-x-y` 升到 `45-x-y`。顺序是：上游分支 → 带回定制提交和补丁 → 两条平台都编过 → 用新的 `45.0.0-cloudbypass.1` 发布。

### 5.1 把上游分支接到 fork

本机 `origin` 的 fetch 是上游：

```powershell
cd D:\electron\main\src\electron
git fetch origin 45-x-y
git checkout -B 45-x-y origin/45-x-y
```

把上一分支上的定制提交拣回来（Electron 源码、`patches/`、文档、类型）。解决冲突后：

```powershell
git push fork HEAD:45-x-y
```

确认 `DEPS` 里的 `chromium_version` 已是目标版本。

### 5.2 补丁冲突

在编译机或本机的 gclient 根：

```bash
cd /src/src/electron
git fetch origin 45-x-y
git checkout -B 45-x-y origin/45-x-y

cd /src/src
git am --abort 2>/dev/null || true
git rebase --abort 2>/dev/null || true

cd /src
e sync --three-way
```

`--three-way` 让补丁在上下文变化时尝试三方合并。仍然冲突时：

1. 看冲突文件：`git -C src diff --name-only --diff-filter=U`（容器里路径是 `/src/src`）。
2. 改完冲突后 `git am --continue`，直到清单里的补丁都进 Chromium 历史。
3. 用 [§2.2](#22-改-chromium必须进补丁) 的导出把新补丁写回 `patches/chromium`，提交并推到 `fork` 的 `45-x-y`。
4. 再跑一次 `e sync --three-way`，确认能从头打完。

若 Chromium 树停在错误提交，或 `git am` 状态坏了：先 `git am --abort`，把 Chromium `reset` 到 `DEPS` 里的版本，再从 gclient 根执行 `apply_all_patches.py`。`reset` / `clean` 时排除 `electron` 和 `out`。

同步结束后抽查定制符号还在，例如：

```bash
grep -n hide_chrome src/third_party/blink/public/common/renderer_preferences/renderer_preferences.h
grep -n SetFilesFromPaths src/third_party/blink/public/web/web_input_element.h
```

### 5.3 编译并发布

按 [§3.3](#33-换大版本时先清构建目录) 删掉旧的 `out`，然后 Windows、Linux 各编一次 `electron:electron_dist_zip`。

`mirror/config.json` 的 `version` 改为新大版本的 `.1`。按 [§4](#4-发布与业务项目更新) 对实际提供的各平台分别编译、验收与发布，业务项目依赖对应平台已发布的版本。当前 Windows x64 发行版本为 `45.0.0-cloudbypass.5`，已完成编译、88 项运行验收与本地镜像安装检查；Linux x64 仍为已有 `.2`，不能随 Windows 版本一起改为 `.5`。

同一大版本里的后续修复只递增末尾序号：`.3`、`.4`，分支仍是 `45-x-y`。

## 6. 一次发布前的核对

- [ ] `src/electron` 在目标分支，且已推到 `fork`
- [ ] Chromium 定制都在 `patches/chromium/.patches` 里，不只有工作区改动
- [ ] `e sync --three-way` 能打完补丁
- [ ] `dist.zip` 里的可执行文件与平台一致（Windows 是 `electron.exe`，Linux 是 `electron`）
- [ ] `mirror/config.json` 的 `version` 是新发布号
- [ ] 该版本的 `SHASUMS256.txt` 包含这次要给出去的每个平台
- [ ] 业务项目 `.npmrc` 仍指向 `mirror.cloudbypass.com`，且 `electron_use_remote_checksums=1`
- [ ] 功能或 API 有变时，`main/docs` 与 `src/electron/docs/zh` 已一起更新
